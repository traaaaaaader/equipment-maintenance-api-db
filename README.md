# Equipment Maintenance API

REST API на Express 5 + TypeScript для учёта оборудования производственной площадки
и заявок на его техническое обслуживание. Сервис контролирует жизненный цикл заявки
(допустимые переходы статуса, включая проверку назначенной бригады) и позволяет оценить
погодные условия на объекте перед планированием наружных работ через внешний погодный API.

Данные хранятся в PostgreSQL через Sequelize (модели, миграции, транзакции). Помимо
оборудования и заявок из Кейса 2, предметная модель расширена площадками, техническими
паспортами оборудования, специалистами и их назначением на заявки бригадами, журналом
смены статусов и учётом расхода запчастей — со сводным отчётом по площадке и
аналитическим SQL-отчётом по нагрузке на оборудование. Сервис
аутентификации и ролевая модель, разворачивает весь стек за обратным прокси Nginx,
подключает мониторинг на Prometheus/Grafana и доводит документацию/тесты до
эксплуатационной готовности.

## Требования к окружению

- Node.js ≥ 20 (Express 5 требует Node ≥ 18)
- npm ≥ 10
- Docker + Docker Compose — **обязательно**: PostgreSQL поднимается только в контейнере,
  локальная установка не поддерживается
- Доступ в интернет — для эндпоинта прогноза погоды (внешний API Open-Meteo, ключ не требуется)

## Установка и запуск

```bash
npm install
cp .env.example .env

docker compose up -d db      # поднять только БД (без сборки контейнера приложения)
npm run db:migrate           # применить миграции
npm run db:seed              # наполнить демо-данными (площадки, оборудование, заявки, …)

npm run start:dev            # разработка, автоперезапуск (nodemon + tsx)
# либо
npm run build && npm start   # сборка в dist/ и запуск скомпилированного кода
```

Сервер поднимается на `http://localhost:3000` (порт настраивается через `PORT`).
Проверка: `curl http://localhost:3000/api/health/ready` — эндпоинт реально ходит в БД
(`sequelize.authenticate()`), а не просто отвечает «процесс жив» (для этого есть отдельный,
более дешёвый `/api/health/live` — см. [Эксплуатационная
инструкция](#эксплуатационная-инструкция)).

Данные хранятся в PostgreSQL (Sequelize, слой репозиториев в `src/repositories/`). Схема
создаётся только миграциями — `sync({ force: true })` в проекте не используется нигде.

### Развёртывание с нуля — по шагам

1. `docker compose up -d db` — контейнер БД с healthcheck, ждём `healthy`
   (`docker compose ps`). При самой первой инициализации (пустой том) Postgres дополнительно
   выполняет скрипты из `db/init/`: `10-create-app-runtime-role.sh` создаёт непривилегированную
   роль `APP_PGUSER` для рантайм-соединения API и базу `PGDATABASE_TEST` для тестов (её не
   создаёт сам образ postgres — он поднимает только `PGDATABASE`); `20-create-grafana-reader-role.sh`
   создаёт read-only роль `grafana_reader` под датасорс Grafana (см. [Мониторинг: Prometheus и
   Grafana](#мониторинг-prometheus-и-grafana)).
2. `npm run db:migrate` — накатывает все миграции по порядку (см. [Миграции и
   сиды](#миграции-и-сиды)).
3. `npm run db:seed` — наполняет базу демо-данными: 3 площадки, 8 единиц оборудования (5 с
   паспортом), 6 специалистов, 6 видов запчастей, 24 заявки в разных статусах и приоритетах
   с журналом смены статусов, назначенными бригадами и списанием запчастей, а также 4 учётные
   записи под каждую роль (см. [Аутентификация и роли](#аутентификация-и-роли)).
4. `npm run start:dev` (или `npm run build && npm start`) — запуск приложения. При
   недоступной БД на старте приложение не падает молча: `waitForDatabase()`
   (`src/db/sequelize.ts`) повторяет попытку подключения с растущей паузой, а если БД так и
   не поднялась — пишет понятную ошибку в лог и завершает процесс с ненулевым кодом, вместо
   зависания без диагностики.

Откат к чистому состоянию — `docker compose down -v && docker compose up -d db` (том с
данными удаляется вместе с контейнером) — и повторить шаги 2–3.

## Запуск через Docker

Полный стек (Nginx, API, PostgreSQL, Prometheus, Alertmanager, Grafana) поднимается одной
командой, без ручных дополнительных шагов:

```bash
cp .env.example .env
docker compose up --build
```

Сборка API — multi-stage (`Dockerfile`): слой `deps` ставит все зависимости, `build`
компилирует TypeScript (`npm run build`) и используется только во время сборки, `migrate` —
отдельный маленький образ только под `sequelize-cli db:migrate` (без `dist/`, не часть
рантайма), `runtime` — чистый финальный образ только с прод-зависимостями (`npm ci --omit=dev`)
и готовым `dist/`, без исходников и без dev-инструментов, запускается от непривилегированного
пользователя `node` (а не root). Compose поднимает:

- `db` — `postgres:18-alpine`, именованный том `pgdata:/var/lib/postgresql` (путь для
  каталога данных изменился начиная с PostgreSQL 18 — старый путь `/var/lib/postgresql/data`
  для этой версии образа не работает), healthcheck на `pg_isready`, порт публикуется только
  на `127.0.0.1` — снаружи напрямую недоступен;
- `migrate` — одноразовый контейнер (`restart: 'no'`), гоняет миграции после
  `db: service_healthy` и завершается; `api` стартует только после его успешного завершения
  (`condition: service_completed_successfully`) — миграции применяются воспроизводимым шагом
  развёртывания, а не вручную «на лету»;
- `api` — читает переменные окружения из `.env` (`env_file`), принудительно выставляет
  `NODE_ENV=production` и `PGHOST=db` поверх него (внутри docker-сети база отвечает по имени
  сервиса, а не по `localhost`), стартует только после `db: service_healthy` и
  `migrate: service_completed_successfully`;
- `tls-init` — одноразовый контейнер, генерирует самоподписанный TLS-сертификат в volume
  `tls-certs` при первом запуске (`deploy/nginx/generate-cert.sh`), если сертификата там ещё нет;
- `nginx` — обратный прокси перед API и Grafana, слушает `80`/`443` (см. [Nginx и
  развёртывание стека](#nginx-и-развёртывание-стека));
- `prometheus`, `alertmanager`, `grafana` — стек мониторинга, поднимается и настраивается
  автоматически (provisioning), без ручной настройки после старта (см. [Мониторинг:
  Prometheus и Grafana](#мониторинг-prometheus-и-grafana)).

`db`, `api` и `nginx` снабжены `HEALTHCHECK` (у `api` — HTTP-запрос к `/api/health/live`, у
`db` — `pg_isready`, у `nginx` — запрос к `/api/health/live` через себя же, то есть проверяет
заодно и то, что проксирование до API работает). Наружу публикуются только порты `nginx`
(`80`/`443`) и `api` (для прямой отладки без прокси — см. [известные
ограничения](#архитектурные-решения-и-известные-ограничения)); `db` слушает только
`127.0.0.1`. Миграции встроены в развёртывание отдельным одноразовым сервисом `migrate` (см.
выше) — после `docker compose up` они уже применены, вручную гонять `npm run db:migrate`
не нужно. Сиды в образ не встроены осознанно (это демонстрационные данные, не часть
production-процесса) — после первого подъёма стека прогоните их один раз с хоста
(`npm run db:seed`, если `PGPORT` опубликован) либо изнутри сети
(`docker compose exec db psql ...` или временный `docker compose run --rm migrate npx sequelize-cli db:seed:all`).

## Архитектура и структура проекта

Слоистая архитектура: **маршруты → контроллеры → сервисы → репозитории**.

```
src/
  app.ts                   # сборка Express-приложения (createApp(), без listen) — используется и в тестах
  index.ts                 # точка входа: createApp().listen(...), graceful shutdown
  config/                  # чтение и валидация переменных окружения (Zod)
  db/sequelize.ts           # инстанс Sequelize, пул соединений, waitForDatabase()
  routes/                  # маршруты: путь + HTTP-метод + validate() + controller
  controllers/             # разбор req.valid → вызов сервиса → HTTP-ответ
  services/                # бизнес-правила: уникальность, переходы статуса, транзакции, погодный сервис
  repositories/            # доступ к данным через Sequelize-модели, изолирован интерфейсом
  models/                  # Sequelize-модели: init() схемы + ассоциации (hasOne/hasMany/belongsToMany), toDto()
  validators/               # Zod-схемы для body/params/query — один файл на сущность/ресурс
  middlewares/              # requestId, http-логирование, валидация, rate limit, auth, metrics, 404, errors
  errors/                   # собственные типы ошибок + маппер кодов SQLSTATE → HTTP
  docs/openapi.ts            # сборка спецификации OpenAPI (swagger-ui-express отдаёт её на /api/docs)
  utils/                    # логгер (pino), AsyncLocalStorage-контекст запроса
db/
  config/config.cjs          # конфиг подключения для sequelize-cli (development/test/production)
  init/                       # shell-скрипты инициализации контейнера Postgres (роли БД)
  migrations/                 # схема БД, только через них (см. "Миграции и сиды")
  seeders/                    # демо-данные, включая учётные записи ролей
tests/                       # Jest + Supertest, интеграционные и репозиторные тесты на отдельной тестовой БД
docs/postman/                 # экспортированная коллекция и окружение Postman
deploy/
  nginx/                      # nginx.conf, страницы ошибок 502/503/504, генерация self-signed TLS
  prometheus/                 # prometheus.yml (scrape-конфиг) + alerts.yml (правила алертинга)
  alertManager/                # alertmanager.yml (маршрутизация алертов)
  grafana/provisioning/         # datasources.yml + dashboards.yml + JSON самого дашборда
```

Сборка приложения (`createApp()` в `src/app.ts`) отделена от запуска сервера (`src/index.ts`):
`createApp()` не вызывает `listen()` и подключается в тестах напрямую через `supertest(createApp())`.

Погодный модуль (`src/services/weatherService.ts`) выделен как отдельный сервис.
Сервис оборудования обращается к нему через обычный импорт функции `getForecastForLocation`.

Валидаторы разбиты по сущностям, а не по роутам: например, назначение бригады
(`request_assignees`) — это отдельная сущность со своей моделью, поэтому его схема лежит в
`validators/requestAssignee.schemas.ts`, а не смешана с `request.schemas.ts`, даже притом что
эндпоинт висит на пути `/api/requests/:id/assignees`. Контроллеры и сервисы, наоборот,
группируются по роуту-владельцу: `requestController.ts` обслуживает все пути `/api/requests/*`,
включая вложенные `assignees` и `history`, делегируя содержательную логику в отдельные сервисы
(`requestAssigneeService`, `requestStatusHistoryService`) — по той же схеме, что и
`equipmentController.getWeather`, который делегирует в `weatherService`, а не пишет логику
работы с погодным API прямо в контроллере.

Аутентификация следует той же схеме: `authController` разбирает запрос и формирует HTTP-ответ
(включая cookie), всю содержательную логику (хеширование пароля, выпуск/ротация токенов,
генерик-сообщение об ошибке входа) несёт `authService`, подпись/проверку JWT и хеширование
refresh-токена для хранения в БД — отдельный `tokenService`, доступ к пользователям и
refresh-токенам — `userRepository`/`refreshTokenRepository`. Проверка подлинности
(`authenticate`) и ролей (`requireRole`) — middleware уровня роутера, применяются точечно на
каждом роутере (`equipmentRouter.use(authenticate)` и т.д.), а не глобально на весь `/api` —
так `health`, `auth/login`, `auth/register` и документация остаются доступны без токена.
ABAC-правило «technician меняет статус только своих заявок» живёт отдельной чистой функцией
(`requestAuthorization.ts`, `assertCanChangeStatus`) — она ничего не знает про Express и
покрыта unit-тестом без БД (`tests/unit/requestAuthorization.test.ts`).

## Модель данных

Схема приведена к третьей нормальной форме: справочные значения (площадка, специалист,
запчасть) вынесены в отдельные таблицы и на них ссылаются по внешнему ключу, а не дублируются
внутри заявки/оборудования; в каждой таблице нет полей, зависящих от чего-либо, кроме её
собственного первичного ключа.

### Оборудование (`equipment`)

| Поле                     | Тип                             | Описание                                                                                   |
| ------------------------ | ------------------------------- | ------------------------------------------------------------------------------------------ |
| `id`                     | string (uuid)                   | генерируется сервером                                                                      |
| `siteId`                 | string (uuid) \| `null`         | ссылка на площадку; необязательное поле при создании/обновлении (см. ниже)                 |
| `name`                   | string, 3–100 символов          | обязательное                                                                               |
| `type`                   | enum                            | `turbine` \| `inverter` \| `sensor` \| `substation`                                        |
| `serialNumber`           | string                          | уникален в пределах системы                                                                |
| `location`               | `{ lat: number, lon: number }`  | координаты объекта                                                                         |
| `status`                 | enum                            | `operational` \| `maintenance` \| `fault` \| `decommissioned` (по умолчанию `operational`) |
| `installedAt`            | ISO-дата                        | не в будущем                                                                               |
| `createdAt`, `updatedAt` | ISO-дата-время                  | проставляются сервером                                                                     |
| `passport`               | объект \| `null` \| отсутствует | технический паспорт (1:1), см. ниже; отсутствует при создании, `null` если паспорта нет    |

`siteId` — необязательное поле и в `createEquipmentSchema`, и в `updateEquipmentSchema`
(UUID; при обновлении можно явно передать `null`, чтобы отвязать оборудование от площадки).
Значение проверяется в `equipmentService` до записи: несуществующий `siteId` — `404 NOT_FOUND`
("Площадка ... не найдена"), а не "сырая" ошибка внешнего ключа из БД. Отдельного
CRUD-эндпоинта для площадок всё ещё нет (площадки заводятся сидом), но привязать к площадке
можно любое оборудование, создаваемое или редактируемое через API, а не только через
сид/миграцию, как было раньше.

## Связи и целостность данных

```
sites ──1:N──► equipment ──1:1──► equipment_passports
                  │
                  └──1:N──► maintenance_requests ──1:N──► request_status_history
                                  │        │
                                  │        └──N:M──► spare_parts        (через request_spare_parts)
                                  │
                                  └──N:M──► technicians                  (через request_assignees)

technicians ──1:1──► users ──1:N──► refresh_tokens
```

Все внешние ключи объявлены с осознанно выбранными правилами `ON DELETE`/`ON UPDATE`
(`ON UPDATE CASCADE` везде — суррогатные `uuid`-ключи не меняются, но правило указано явно, а
не полагается на поведение по умолчанию):

| Связь                                                         | `ON DELETE`                                 | Почему                                                                                                                                                                                                               |
| ------------------------------------------------------------- | ------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `equipment.site_id → sites.id`                                | `RESTRICT`                                  | нельзя молча потерять привязку оборудования к площадке; `site_id` при этом **nullable** — оборудование может существовать без площадки                                                                               |
| `equipment_passports.equipment_id → equipment.id`             | `CASCADE`                                   | паспорт не имеет смысла без своего оборудования                                                                                                                                                                      |
| `maintenance_requests.equipment_id → equipment.id`            | `RESTRICT`                                  | оборудование, у которого есть заявки (в том числе закрытые), не должно исчезать бесследно — на практике `equipment` ещё и `paranoid` (мягкое удаление), поэтому реальный `DELETE` до этой проверки обычно не доходит |
| `request_status_history.request_id → maintenance_requests.id` | `CASCADE`                                   | журнал бессмысленен без своей заявки                                                                                                                                                                                 |
| `request_assignees.request_id → maintenance_requests.id`      | `CASCADE`                                   | назначения удаляются вместе с заявкой                                                                                                                                                                                |
| `request_assignees.technician_id → technicians.id`            | `RESTRICT`                                  | нельзя удалить специалиста, у которого есть назначения (в API удаления специалистов и нет)                                                                                                                           |
| `request_spare_parts.*`                                       | `CASCADE` от заявки, `RESTRICT` от запчасти | та же логика, что и у `request_assignees`                                                                                                                                                                            |
| `users.technician_id → technicians.id`                        | `SET NULL`                                  | удаление специалиста не должно удалять учётную запись — она просто перестаёт быть привязана к бригаде, роль у пользователя при этом не меняется автоматически                                                        |
| `refresh_tokens.user_id → users.id`                           | `CASCADE`                                   | сессии бессмысленны без своего пользователя                                                                                                                                                                          |

Оборудование (`equipment`) — `paranoid`-модель Sequelize: `DELETE /api/equipment/:id` не
удаляет строку физически, а проставляет `deleted_at`. Благодаря этому `ON DELETE RESTRICT` на
`maintenance_requests.equipment_id` на практике не мешает пользовательскому сценарию удаления
(проверка «нет открытых заявок» — на уровне сервиса, см. [Состав API](#состав-api)), а
исторические заявки не остаются с оборванной ссылкой на несуществующее оборудование.

Классическая проблема `paranoid` + `UNIQUE`: обычное ограничение уникальности на
`serial_number` продолжало бы блокировать создание нового оборудования с тем же номером даже
после «удаления» старого — строка ведь физически остаётся в таблице. Решено частичным уникальным
индексом вместо обычного ограничения (миграция
`20260927100300-paranoid-unique-and-search-indexes`):

```sql
CREATE UNIQUE INDEX equipment_serial_number_active_uk
  ON equipment (serial_number)
  WHERE deleted_at IS NULL;
```

Уникальность по-прежнему действует среди активных записей (повторный `serialNumber` без
удаления старой записи — `409`), но после `DELETE` номер становится свободен для нового
оборудования. Проверено тестом `tests/repositories/equipmentRepository.test.ts` на обоих
сценариях.

## Миграции и сиды

Схема создаётся **только** миграциями (`sequelize-cli`); `sequelize.sync()` в проекте не
используется нигде. Миграции разбиты по смысловым блокам — так откат/повтор конкретного блока
не задевает остальные:

| Файл                                                      | Что создаёт                                                                                                                                                                                                 |
| --------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `20260927100000-create-equipment-and-requests`            | `equipment`, `maintenance_requests`, `equipment_passports` — перенос Кейса 2 + паспорт                                                                                                                      |
| `20260927100100-create-sites-technicians-and-assignments` | `sites`, колонка `equipment.site_id` (добавляется отдельно — `sites` физически не существует в момент создания `equipment` в первой миграции), `technicians`, `request_status_history`, `request_assignees` |
| `20260927100200-create-spare-parts`                       | `spare_parts`, `request_spare_parts`                                                                                                                                                                        |
| `20260927100300-paranoid-unique-and-search-indexes`       | частичный уникальный индекс на `equipment.serial_number` (совместимость `paranoid` с уникальностью) + GIN-индексы по триграммам для `?search=`                                                              |
| `20260927100400-add-closed-at-to-maintenance-requests`    | колонка `maintenance_requests.closed_at` — момент перехода в терминальный статус, отдельно от `updated_at`                                                                                                  |
| `20260927100500-create-users-and-refresh-tokens`          | `users` (роли, `technician_id`), `refresh_tokens` — аутентификация и ролевая модель                                                                                                                 |

```bash
npm run db:migrate            # применить все миграции по порядку
npm run db:migrate:status     # какие применены, какие нет
npm run db:migrate:undo       # откатить последнюю
npm run db:migrate:undo:all   # откатить всё — таблицы падают в обратном порядке
```

Каждая миграция реализует рабочий `down()`: полный цикл «применить всё → откатить всё →
применить снова» проверен вручную и проходит без ошибок. `dropTable` в Sequelize сам по себе
**не** удаляет связанные Postgres ENUM-типы — каждый `down()`, создавший `ENUM`-колонку, явно
вызывает специализированный метод `queryInterface.dropEnum(enumName)` (Postgres-диалект
Sequelize; формирует `DROP TYPE IF EXISTS "..."` сам, без ручной сборки SQL-строки) после
`dropTable`; после `db:migrate:undo:all` в схеме не остаётся ни одного из 8 созданных
ENUM-типов, включая `enum_users_role` (проверено запросом к `pg_type` — полный цикл
«накатить → откатить всё → накатить снова» прогнан вживую). Миграция
`20260927100300-paranoid-unique-and-search-indexes` восстанавливает в `down()` обычный
(не частичный) `UNIQUE` на `equipment.serial_number` — если за время действия частичного
индекса один и тот же `serial_number` оказался и у мягко удалённой записи, и у новой активной
(ровно то, что частичный индекс и должен разрешать), `down()` сперва переименовывает
`serial_number` у конфликтующих уже удалённых записей (суффиксом `__deleted_<id>`), не трогая
активные, и только потом добавляет ограничение — иначе `ADD CONSTRAINT UNIQUE` падает на дубле.

Сиды (`npm run db:seed` / `npm run db:seed:undo`) наполняют базу данными, которых хватает,
чтобы продемонстрировать все связи и оба отчёта: 3 площадки, 8 единиц оборудования (5 с
паспортом), 6 специалистов, 6 видов запчастей, 24 заявки во всех статусах и приоритетах с
журналом переходов, назначенными бригадами (везде ровно один `lead`) и списанием запчастей, а
также по одной учётной записи на каждую роль (`20260927120100-auth-accounts`, пароль у всех —
`ChangeMe123!`): `admin@example.com` (admin), `ivanov@example.com`/`smirnova@example.com`
(technician, привязаны к специалистам из бригад, которые уже назначены в демо-заявках) и
`viewer@example.com` (viewer). Перенос данных из файлового хранилища Кейса 2 не выполняется —
то хранилище было `in-memory` (`Map` в процессе), без персистентных файлов, переносить
физически нечего.

## Переходы статуса заявки

```
new ───────► in_progress ───────► done
 │                │
 └──► rejected ◄──┘
```

Разрешено: `new → in_progress`, `new → rejected`, `in_progress → done`, `in_progress → rejected`.
Из `done` и `rejected` переходов нет — это терминальные статусы. Таблица переходов живёт в
сервисном слое (`src/services/requestStatusTransitions.ts`). Недопустимый переход отклоняется
с кодом `409 CONFLICT`.

Дополнительное правило: перевод в `in_progress` требует хотя бы одного назначенного
исполнителя (`request_assignees`) — иначе тоже `409 CONFLICT`. Сначала бригада назначается
через `POST /api/requests/:id/assignees`.

Каждый успешный переход статуса выполняется одной транзакцией: обновление
`maintenance_requests.status` и добавление записи в `request_status_history` — вместе или
ни одного (`requestService.changeStatus`, `src/services/requestService.ts`).

## Аутентификация и роли

### Роли

| Роль         | Права                                                                                                       |
| ------------ | ----------------------------------------------------------------------------------------------------------- |
| `viewer`     | Чтение справочников, заявок, истории и отчётов                                                              |
| `technician` | Права `viewer` + создание и редактирование заявок, смена статуса **только тех заявок, на которые назначен** |
| `admin`      | Все операции, включая управление оборудованием, площадками, назначение бригад и удаление                    |

По умолчанию при регистрации выдаётся `viewer`; повышение роли — только через
`PATCH /api/users/:id/role` от имени `admin` (см. таблицу эндпоинтов ниже). Разграничение
реализовано в двух слоях: `requireRole(...roles)` — ролевая проверка (RBAC) на уровне
роутера, и `assertCanChangeStatus` (`src/services/requestAuthorization.ts`) — атрибутная
проверка (ABAC) внутри `requestService.changeStatus`, сверяющая факт назначения technician'а
именно на эту заявку через `request_assignees`.

| Метод | Путь                  | Назначение                                         | Auth                       |
| ----- | --------------------- | -------------------------------------------------- | -------------------------- |
| POST  | `/api/auth/register`  | Регистрация (по умолчанию роль `viewer`)           | —                          |
| POST  | `/api/auth/login`     | Вход, выдача access-токена и refresh-cookie        | — (своя AUTH_RATE_LIMIT_*) |
| POST  | `/api/auth/refresh`   | Обновление access-токена по refresh-cookie         | refresh-cookie             |

| GET   | `/api/auth/me`        | Текущий пользователь и его роль                    | 🔑                         |
| GET   | `/api/users`          | Список пользователей (фильтр по роли)              | 🔑 admin                   |
| PATCH | `/api/users/:id/role` | Смена роли пользователя (и привязки к специалисту) | 🔑 admin                   |

### Пароли, токены, cookie

- Пароли хранятся только как bcrypt-хеш (`bcryptjs`, `src/utils/password.ts`) — ни хеш, ни
  пароль не попадают в ответы API, логи (`redact` у pino, см. [Логирование](#логирование)) и
  DTO моделей (см. [Модель данных](#модель-данных)).
- Access-токен — JWT (`JWT_ACCESS_SECRET`, по умолчанию 15 минут — `JWT_ACCESS_TTL_MS`),
  передаётся заголовком `Authorization: Bearer <token>`, содержит `sub`, `role`,
  `technicianId`. Секрет берётся из переменных окружения, в коде не хардкодится.
- Refresh-токен — отдельный JWT с собственным секретом (`JWT_REFRESH_SECRET`, по умолчанию
  7 дней — `JWT_REFRESH_TTL_MS`), передаётся cookie `refreshToken` с флагами `HttpOnly`,
  `Secure` (в `production`) и `SameSite=Strict`, `path=/api/auth`. В БД (`refresh_tokens`)
  хранится не сам токен, а его SHA-256-хеш (`tokenService.hashRefreshToken`) — утечка дампа БД
  не даёт готовых токенов для угона сессии. При каждом `POST /api/auth/refresh` старый токен
  немедленно отзывается (`revokedAt`), выдаётся новый (ротация); если на вход пришёл токен,
  который уже отозван (повторное использование — признак кражи), все refresh-токены
  пользователя отзываются разом (`refreshTokenRepository.revokeAllForUser`) и клиент обязан
  залогиниться заново. `POST /api/auth/logout` отзывает refresh-токен и чистит cookie.
- `SameSite=Strict`, а не `Lax`: UI и API в этом проекте обслуживаются одним origin,
  кросс-сайтовые запросы с cookie не нужны, поэтому выбран более строгий вариант.
- Эндпоинт входа защищён отдельным `authRateLimiter` (`AUTH_RATE_LIMIT_MAX` попыток за
  `AUTH_RATE_LIMIT_WINDOW_MS`, ключ — IP + email), независимым от общего `apiRateLimiter`.
  Ответ на неуспешный вход («нет такого пользователя» и «неверный пароль») — один и тот же
  текст и код (`401 UNAUTHORIZED`, «Неверные учётные данные») — не раскрывает существование
  учётной записи.
- Изменяющие операции защищены `authenticate` + `requireRole(...)`: запрос без токена — `401`,
  запрос с валидным токеном, но недостаточной ролью — `403`. Чтение (`GET`) доступно любому
  аутентифицированному пользователю независимо от роли.

### Query-параметры списочных эндпоинтов

Общие: `page` (по умолчанию 1), `limit` (по умолчанию 20, максимум 100), `sort` (имя поля,
префикс `-` — убывающий порядок, например `sort=-createdAt`).

- `GET /api/equipment`: `type`, `status`, `search` (по имени/серийному номеру). Поля сортировки:
  `name`, `installedAt`, `createdAt`, `status`, `type`.
- `GET /api/requests`: `status`, `priority`, `equipmentId`, `createdFrom`/`createdTo`,
  `plannedFrom`/`plannedTo` (диапазоны ISO-дат-времени). Поля сортировки: `createdAt`,
  `updatedAt`, `plannedAt`, `priority`, `status`.
- `GET /api/equipment/:id/requests` (вложенный ресурс): `status`, `priority`, `sort` — те же
  правила, но без `equipmentId` (он берётся из пути) и без диапазонов дат.
- `GET /api/requests/:id/history`: только `page`/`limit` (сортировка фиксирована —
  по времени перехода, от старых к новым).
- `GET /api/reports/equipment-load`: `dateFrom`/`dateTo` (диапазон по дате создания заявки,
  ISO-дата-время) и `minRequests` (минимальное число заявок у оборудования — фильтрация групп
  результата, `HAVING`, а не `WHERE`); без пагинации, группа — одна строка на единицу
  оборудования.

Некорректные значения параметров (например, `page=abc`, `status=unknown`, `minRequests=-1`)
отклоняются валидатором с кодом `422`. Поле сортировки (`sort`) и его направление всегда
проверяются по белому списку допустимых значений — значение из query-строки никогда не
подставляется в `ORDER BY` напрямую (см. [Защита от SQL-инъекций](#защита-от-sql-инъекций)).
`limit` ограничен сверху схемой (максимум 100) на всех списочных эндпоинтах без исключений —
клиент не может запросить произвольно большую выборку.

## Формат ответа

Единая форма для всех успешных ответов:

```json
// один объект
{ "data": { "id": "…", "...": "..." } }
```

```json
// список
{
  "data": [{ "id": "…" }, { "id": "…" }],
  "meta": { "total": 42, "page": 1, "limit": 20 }
}
```

Коды ответов: `200` — чтение/обновление, `201` — создание (с заголовком `Location`, указывающим
на созданный ресурс), `204` — удаление (без тела), `400` — синтаксически некорректное тело
запроса («битый» JSON, ошибка парсера `express.json()`), `401` — отсутствует или невалиден/истёк
access-токен, `403` — валидный токен, но роль не позволяет операцию (в т.ч. technician вне своей
бригады) или источник не разрешён политикой CORS, `404` — ресурс не найден, `409` — конфликт
состояния (дубль серийного номера, недопустимый переход статуса, удаление оборудования с
открытыми заявками), `413` — тело запроса превышает `BODY_LIMIT`, `422` — тело/параметры не
проходят схему валидации, `429` — превышен лимит частоты запросов (общий или отдельный лимит
входа), `503` — внешний погодный API или БД недоступны.

## Формат ответа об ошибке

Единый для всего API, формируется только в централизованном обработчике ошибок
(`src/middlewares/errorHandler.ts`):

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Некорректные данные запроса",
    "details": [
      {
        "field": "body.priority",
        "message": "priority должен быть одним из: low, medium, high, critical"
      }
    ],
    "requestId": "b1f2c3d4-1234-4a5b-9abc-1234567890ab"
  }
}
```

`requestId` есть в каждом ответе об ошибке и в заголовке `X-Request-Id` каждого ответа
(успешного тоже) — по нему запрос находится в логах сервера. `details` присутствует только
там, где есть что перечислить (ошибки валидации и часть конфликтов). В `production`
(`NODE_ENV=production`) в ответ никогда не попадают стек-трейсы и внутренние сообщения об
ошибках 5xx — только нейтральный текст и `requestId`; в `development` для 5xx дополнительно
добавляется `error.stack`, чтобы ускорить отладку.

Коды ошибок: `VALIDATION_ERROR` (422), `BAD_REQUEST` (400/413 — «битый» JSON или превышен
`BODY_LIMIT`), `UNAUTHORIZED` (401), `FORBIDDEN` (403, в т.ч. CORS), `NOT_FOUND` (404),
`CONFLICT` (409), `UNPROCESSABLE_ENTITY` (422 — ошибка внешнего ключа БД, см. ниже),
`SERVICE_UNAVAILABLE` (503, недоступен внешний погодный API), `RATE_LIMIT_EXCEEDED` (429),
`INTERNAL_ERROR` (500).

### Ошибки базы данных, не пойманные заранее в сервисах

Там, где бизнес-логика уже отсекает нарушение до похода в БД (например, дубль
`serialNumber` проверяется в `equipmentService.create` до `INSERT`), клиент видит понятную
ошибку сразу. Но часть нарушений (в первую очередь — гонки при параллельных запросах: два
клиента одновременно проходят пред-проверку и оба пытаются вставить одно и то же) добираются
до реального ограничения в PostgreSQL. Такие ошибки не должны превращаться в «сырые» `500` —
`src/errors/databaseErrorMapper.ts` переводит код `SQLSTATE` от Postgres (`err.parent.code` у
Sequelize, `err.code` у голого `pg`) в тот же единый формат ответа:

| SQLSTATE          | Значение                                    | HTTP                                                                                                                                      |
| ----------------- | ------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- |
| `23505`           | `unique_violation`                          | `409 CONFLICT`                                                                                                                            |
| `23503`           | `foreign_key_violation`                     | `422 UNPROCESSABLE_ENTITY`                                                                                                                |
| `23502`           | `not_null_violation`                        | `400 BAD_REQUEST`                                                                                                                         |
| `23514`           | `check_violation`                           | `422 UNPROCESSABLE_ENTITY`                                                                                                                |
| `40001` / `40P01` | конфликт сериализации / взаимная блокировка | `409 CONFLICT` (в проекте не используется `SERIALIZABLE`/повторные попытки, но по чек-листу эти коды тоже не должны превращаться в `500`) |

Текст самой ошибки БД (имена таблиц, колонок, ограничений) наружу никогда не уходит — только
код и заранее заданное нейтральное сообщение из таблицы выше; полная ошибка со стеком остаётся
в логе сервера. Проверено на настоящих ошибках Postgres (не выдуманных): `23505`, `23503` и
`23514` воспроизведены напрямую через репозитории в обход сервисных проверок — см. тесты в
`tests/databaseErrorMapper.test.ts`. Код `23502` в этом проекте фактически недостижим: модели
Sequelize уже объявляют `allowNull: false` там же, где миграция объявляет `NOT NULL`, поэтому
такое нарушение перехватывается самим Sequelize на стороне приложения (`SequelizeValidationError`)
раньше, чем запрос вообще уходит в базу.

### Сводка по площадке

```
GET /api/sites/11111111-1111-4111-8111-000000000001/summary
```

```
200 OK

{
  "data": {
    "siteId": "11111111-1111-4111-8111-000000000001",
    "totalRequests": 9,
    "byStatus": { "new": 2, "in_progress": 4, "done": 2, "rejected": 1 },
    "byPriority": { "low": 2, "medium": 4, "high": 2, "critical": 1 },
    "averageCloseTimeHours": 96.5
  }
}
```

`averageCloseTimeHours` — `null`, если у площадки ещё нет ни одной заявки в статусе `done`
(делить не на что); отсутствующие статусы/приоритеты в выборке возвращаются нулём, а не
пропускаются, чтобы клиенту не приходилось на них проверять.

Считается как `avg(closed_at - created_at)` по выделенной колонке `maintenance_requests.closed_at`,
а не по `updated_at`: `updated_at` меняется любым `PATCH /api/requests/:id` (например, правкой
`description` уже закрытой заявки), и среднее «время закрытия» начинало бы скакать от
редактирования текста, не имеющего отношения к длительности обслуживания. `closed_at`
проставляется один раз — в момент перехода в `done`/`rejected` (`requestService.changeStatus`) —
и больше не трогается.

## Погодный сервис и пригодность окна для работ

`GET /api/equipment/:id/weather` берёт координаты оборудования, обращается к внешнему
погодному API [Open-Meteo](https://open-meteo.com/) (не требует API-ключа) и возвращает
текущие погодные показатели вместе с флагом пригодности окна для наружных работ:

```json
{
  "data": {
    "location": { "lat": 55.7558, "lon": 37.6173 },
    "current": { "temperature_2m": 18.7, "precipitation": 0, "wind_speed_10m": 10.7 },
    "outdoorWorkWindow": {
      "suitable": true,
      "reasons": [],
      "thresholds": { "maxWindKmh": 40 }
    }
  }
}
```

Правило пригодности (задаётся в конфигурации, переменная `WEATHER_MAX_WIND_KMH`): **отсутствие
осадков и скорость ветра ниже порога**. Если правило не выполняется, `suitable: false`, а
`reasons` перечисляет, какое именно условие нарушено.

Недоступность или ошибка внешнего API **не приводит к падению сервиса**: любая проблема
(таймаут, сетевая ошибка, `5xx`/некорректный ответ у Open-Meteo) оборачивается в
`WeatherServiceError` и обрабатывается тем же централизованным обработчиком ошибок, возвращая
клиенту `503 SERVICE_UNAVAILABLE` с понятным сообщением, а не необработанное исключение.

## Транзакции и конкурентный доступ

Многошаговые операции, меняющие больше одной таблицы, выполняются одной управляемой
транзакцией Sequelize (`sequelize.transaction(async (t) => { ... })`) — при исключении внутри
колбэка откат происходит автоматически, соединение возвращается в пул в любом исходе:

- **Смена статуса заявки** (`requestService.changeStatus`) — обновление
  `maintenance_requests.status` и вставка строки в `request_status_history` вместе.
- **Назначение бригады** (`requestAssigneeService.assign`) — снятие прежних назначений,
  проверка существования всех специалистов, вставка новых; `transaction: t` передан во все
  без исключения запросы внутри операции.
- **Списание запчасти** (`requestSparePartService.consume`) — атомарное уменьшение
  остатка и фиксация расхода по заявке.

Внутри всех транзакций нет ни HTTP-вызовов, ни файловых операций, ни ожидания
пользовательского ввода — только запросы к БД, чтобы не удерживать соединение из пула дольше
необходимого.

### Защита от гонки при конкурентном изменении одной заявки

Смена статуса — классический пример «прочитать — проверить — записать»: сервис читает текущий
статус, проверяет допустимость перехода, затем пишет новый. Если бы статус читался **до**
транзакции (как было в первой версии кода), два параллельных запроса на смену статуса одной и
той же заявки могли бы оба прочитать один и тот же исходный статус, оба пройти проверку и оба
записать в историю переходы, один из которых на момент записи уже не соответствовал
действительности.

Решение — блокировка строки внутри транзакции: `requestRepository.findStatusForUpdate()` делает
`SELECT status FROM maintenance_requests WHERE id = $1 FOR UPDATE` (`lock: transaction.LOCK.UPDATE`
у Sequelize) **после** начала транзакции, а не до неё. Второй параллельный запрос дожидается
коммита первого и повторно проверяет допустимость перехода уже по актуальному статусу — если
переход больше не имеет смысла (например, оба запроса пытались перевести заявку в `in_progress`),
второй получает `409`, а не тихо перезаписывает историю. Проверено тестом с двумя одновременными
запросами (`tests/concurrency.test.ts`): ровно один из двух получает `200`, второй — `409`, в
журнале статусов остаётся ровно одна запись перехода, а не две.

Проверка «нет ли уже такого специалиста в бригаде» намеренно не делается запросом «прочитать —
проверить — записать»: вместо этого дубликат внутри одного присланного списка отклоняется ещё до
транзакции (`ConflictError`, 409), а уникальность пары (заявка, специалист) на уровне уже
существующих в БД строк гарантирует ограничение `UNIQUE` в схеме — обойти его невозможно даже
если бы проверка в коде была написана неправильно. Списание запчасти защищено похожим образом,
но через атомарный `UPDATE`, а не блокировку строки (см. ниже).

### Атомарный UPDATE вместо блокировки — списание запчасти

Для списания остатка используется другой из двух способов защиты от гонки, разобранных в
теории, — атомарное условие в самом `UPDATE`, а не отдельная блокировка строки
(`requestSparePartRepository.decrementStock`):

```sql
UPDATE spare_parts
   SET quantity = quantity - $1
 WHERE id = $2 AND quantity >= $1
 RETURNING id, quantity
```

Если остатка не хватает, условие `quantity >= $1` не выполняется, `RETURNING` не возвращает ни
одной строки — и это единственный сигнал, который нужен сервису, чтобы отдать `409` с точным
остатком в сообщении. Два параллельных списания одного и того же остатка база сериализует сама,
без блокировок на стороне приложения.

## SQL-отчёты

`GET /api/reports/equipment-load` — прямой SQL-запрос (не через Sequelize query builder) с
`JOIN` трёх таблиц, агрегатными функциями и группировкой:

```sql
SELECT
  e.id, e.name, e.serial_number,
  count(DISTINCT mr.id)                                   AS total_requests,
  count(DISTINCT mr.id) FILTER (WHERE mr.status = 'done')  AS closed_requests,
  coalesce(sum(ra.planned_hours), 0)                       AS total_planned_hours,
  max(mr.closed_at) FILTER (WHERE mr.status = 'done')      AS last_maintenance_at
FROM equipment e
LEFT JOIN maintenance_requests mr ON mr.equipment_id = e.id AND (период по $1/$2)
LEFT JOIN request_assignees ra ON ra.request_id = mr.id
WHERE e.deleted_at IS NULL
GROUP BY e.id, e.name, e.serial_number
HAVING count(DISTINCT mr.id) >= $3
ORDER BY e.name
```

Два момента, из-за которых запрос не самый очевидный:

- `count(DISTINCT mr.id)`, а не `count(mr.id)` — второй `LEFT JOIN` на `request_assignees`
  размножает строки (одна заявка с двумя специалистами даёт две строки после джойна), и без
  `DISTINCT` число заявок оказалось бы задвоено для любой заявки с более чем одним
  исполнителем.
- условие периода (`dateFrom`/`dateTo`) стоит в `ON` у `LEFT JOIN`, а не в `WHERE` — иначе
  оборудование без единой заявки за выбранный период вообще пропало бы из отчёта, а не
  показалось бы с нулевыми счётчиками.

`GET /api/sites/:id/summary` реализован тремя более простыми запросами (счёт по статусам, счёт
по приоритетам, среднее время закрытия) вместо одного сложного — каждый читается по отдельности
и проще объяснить на защите, чем один запрос с несколькими условными агрегатами.

## Защита от SQL-инъекций

- Все прямые SQL-запросы (`sequelize.query(...)` в `siteRepository.ts`, `reportRepository.ts`)
  передают значения только через `bind: [...]` и плейсхолдеры `$1`, `$2`, … — ни одного места,
  где пользовательский ввод попадал бы в текст запроса склейкой строк.
- Поле сортировки (`sort`) и его направление проверяются по белому списку на уровне
  Zod-схемы (`sortSchema()`, `src/validators/common.schemas.ts`) до того, как значение попадёт
  в `ORDER BY` — идентификатор колонки нельзя параметризовать через `$1`, поэтому единственная
  защита здесь — не пускать в запрос ничего, кроме заранее перечисленных имён полей.
- Поиск (`?search=`) идёт через `Op.iLike`, что тоже параметризуется драйвером — значение
  остаётся данными, а не текстом запроса, попытка передать в `search` фрагмент SQL просто не
  находит совпадений, а не изменяет структуру запроса.
- `limit`/`offset` ограничены сверху схемой валидации на всех списочных эндпоинтах.
- Учётные данные БД — только в переменных окружения, не в коде и не в репозитории.

Всё это проверено не только по коду, но и вживую: `search` со значением вида
`' OR '1'='1` и `WTG'; DROP TABLE equipment; --` возвращает пустой список без ошибок, таблица
после такого запроса остаётся на месте.

## Политики безопасности

- **CORS** — явный список разрешённых источников из `CORS_ORIGINS` (никогда `*`). По умолчанию
  разрешён только `http://localhost:3000`; для фронтенда, задеплоенного отдельно, впишите его
  адрес через запятую. Разрешённые методы ограничены реально используемыми
  (`GET, POST, PATCH, DELETE`). Запрос с несогласованным `Origin` отклоняется с `403 FORBIDDEN`
  через тот же централизованный обработчик ошибок, а не generic-ответом библиотеки `cors`.
- **Rate limiting** — `express-rate-limit` на всех маршрутах `/api`: `RATE_LIMIT_MAX` запросов
  за `RATE_LIMIT_WINDOW_MS` на IP. При превышении — `429` с заголовками `RateLimit-*`
  (draft-7) и телом в едином формате ошибок API.
- **Ограничение размера тела** — `express.json({ limit: BODY_LIMIT })`, по умолчанию `100kb`:
  запрос с более крупным телом отклоняется до попадания в бизнес-логику (`413`).
- **Защитные заголовки** — `helmet()`. HSTS включается только при `NODE_ENV=production`:
  заголовок `Strict-Transport-Security` имеет смысл только при реальном HTTPS, а в разработке
  сервис работает по обычному HTTP, поэтому в dev-режиме заголовок не отправляется. Также явно
  отключён `X-Powered-By` (`app.disable('x-powered-by')`).
- **Секреты** — не хранятся в репозитории: `.env` в `.gitignore`, в коде только чтение из
  `process.env` через `src/config`. В `.env.example` — только безопасные dev-плейсхолдеры
  (пароли/секреты JWT с суффиксом `change_me`/`dev_local_...`), реальных значений нет.
- **Cookie** — единственная cookie в проекте — `refreshToken` (см. [Аутентификация и
  роли](#аутентификация-и-роли)): `HttpOnly` (недоступна из JS, не читается XSS-полезной
  нагрузкой), `Secure` в `production` (передаётся только по HTTPS), `SameSite=Strict` (весь
  UI и API — один origin, кросс-сайтовые запросы с этой cookie не нужны), `path=/api/auth`
  (cookie не уходит ни в один другой эндпоинт, кроме `refresh`/`logout`).
- **Пользователь БД** — учётные данные только в переменных окружения, ни в коде, ни в
  репозитории. Рантайм-соединение самого API и привилегированная роль для миграций разделены:
  `PGUSER`/`PGPASSWORD` — это `POSTGRES_USER` из `docker-compose.yaml`, которым Postgres
  инициализирует кластер в контейнере (фактически суперпользователь этого инстанса); он
  используется только `sequelize-cli` (миграции, сиды) и тестами (фикстурам нужен `TRUNCATE`).
  Сам же API (`src/db/sequelize.ts`, и в `development`, и в `production`) подключается
  отдельной ролью `APP_PGUSER`/`APP_PGPASSWORD` без `CREATEDB`/DDL-прав — только
  `SELECT/INSERT/UPDATE/DELETE` по таблицам приложения. Эта роль и права на неё
  (`GRANT ... ON ALL TABLES IN SCHEMA public` + `ALTER DEFAULT PRIVILEGES` — чтобы право
  распространялось и на таблицы, которые миграции создадут позже) заводятся автоматически при
  первой инициализации контейнера БД (`db/init/10-create-app-runtime-role.sh`, монтируется в
  `/docker-entrypoint-initdb.d`). Проверено вживую: под `APP_PGUSER` обычный `SELECT`/`INSERT`
  проходит, а `CREATE TABLE` и `TRUNCATE` — `permission denied`.

## Логирование

- Каждый входящий запрос логируется через `pino-http`: метод, путь, код ответа, длительность,
  `reqId`. Уровень подбирается автоматически: `error` — 5xx, `warn` — 4xx, `info` — успех.
- Идентификатор запроса присваивается в самом начале конвейера (`src/middlewares/requestId.ts`,
  до логирования), возвращается клиенту в заголовке `X-Request-Id` и в `error.requestId` —
  по нему конкретный запрос находится в логах одной фильтрацией.
- Сервисы и репозитории не получают `req` как аргумент, но могут логировать с тем же `reqId`
  через `AsyncLocalStorage` (`src/utils/context.ts`, `getLog()`).
- Уровни логирования: `fatal`/`error`/`warn`/`info`/`debug` (pino, `LOG_LEVEL`). В коде нет
  вызовов `console.log`; вывод в `development` дополнительно проходит через `pino-pretty` для
  читаемости, в `test` логирование отключено (`level: 'silent'`), чтобы не засорять вывод
  тестов.
- В логи не попадают заголовки `Authorization`/`Cookie` и поля `password`/`passwordHash` в
  логируемых объектах (настройка `redact` у pino, `src/utils/logger.ts`).
- В разработке (`NODE_ENV != test`) каждый SQL-запрос логируется на уровне `debug`
  (`src/db/sequelize.ts`, опция `logging` у `Sequelize`) — по нему в первую очередь и
  проверяется, что транзакция реально передана во все запросы операции, а не ушла мимо неё по
  отдельному соединению из пула. В `test` логирование БД отключено, чтобы не засорять вывод
  тестов.

## Nginx и развёртывание стека

Целевая схема: `клиент → nginx (:80/:443) → api (:3000) → postgres`, Grafana подключена к
`nginx` отдельным location, `/metrics` API скрейпит `prometheus` напрямую по внутренней сети
(наружу не публикуется). Конфигурация — `deploy/nginx/nginx.conf`, монтируется в контейнер
`nginx` read-only (`docker-compose.yaml`), применяется при каждом `docker compose up` — никакой
отдельной ручной настройки не требуется.

- **HTTP → HTTPS** — `:80` отвечает только `308`-редиректом на `https://…`; весь реальный
  трафик обслуживается на `:443`. Сертификат — самоподписанный, генерируется одноразовым
  контейнером `tls-init` (`deploy/nginx/generate-cert.sh`) в volume `tls-certs` при первом
  запуске стека (имя хоста — `NGINX_SERVER_NAME`, по умолчанию `localhost`); для реального
  домена сюда подставляется сертификат от внешнего CA.
- **Заголовки безопасности** — `Strict-Transport-Security`, `X-Content-Type-Options: nosniff`,
  `X-Frame-Options: DENY`, `Referrer-Policy`, плюс `X-Request-ID` прокидывается в ответ клиенту.
- **Проброс клиентского контекста** — `Host`, `X-Real-IP`, `X-Forwarded-For`,
  `X-Forwarded-Proto` на всех запросах к API; в приложении включено доверие прокси
  (`app.set('trust proxy', 1)`, `src/app.ts`), поэтому `req.ip` и rate limiting в API видят
  реальный IP клиента, а не IP контейнера `nginx`.
- **Таймауты и лимиты** — `proxy_connect_timeout 5s`, `proxy_send/read_timeout 30s`,
  `client_max_body_size 1m` (с запасом над прикладным `BODY_LIMIT`), `gzip` на JSON/текстовых
  ответах.
- **Rate limiting на уровне прокси** — `limit_req_zone` (20 req/s на IP, burst 40) на `/api/`
  как дополнительный защитный слой перед прикладным `apiRateLimiter`.
- **Маршрутизация по `location`** — `/api/` проксируется на `api` через `upstream api_upstream`
  (`server api:3000 resolve;` + `resolver 127.0.0.11` — динамическое DNS-разрешение имени
  сервиса, поэтому `nginx` не падает, если стартовал раньше `api`, и подхватывает контейнер
  заново после его перезапуска); `/grafana/` — через аналогичный `upstream grafana_upstream`
  на `grafana`; `/` редиректит на `/api/docs`; неизвестные пути получают стандартный `404` от
  `nginx` (запрос до API не доходит). Ошибки апстрима (`502`/`503`/`504`) подменяются
  JSON-страницами (`deploy/nginx/errors/`) в том же формате, что и ошибки самого API — клиент
  не видит HTML-страницу nginx по умолчанию.
- **Доступ к служебным путям** — `/metrics` не проксируется через `nginx` вообще (Prometheus
  скрейпит `api:3000/metrics` напрямую по internal docker-сети, снаружи этот путь недостижим);
  `/grafana/` в текущей версии проксируется без дополнительного ограничения (это известное
  ограничение — см. [Архитектурные решения и известные
  ограничения](#архитектурные-решения-и-известные-ограничения)): доступ в Grafana закрывается
  собственным логином (`GRAFANA_ADMIN_USER`/`GRAFANA_ADMIN_PASSWORD`), но IP-allowlist/basic
  auth на уровне `nginx` для этого location ещё не добавлены.

Сервис (`api`) не публикует порт наружу напрямую для конечного пользователя — предполагаемый
вход только через `nginx`; порт `api` в `docker-compose.yaml` опубликован для локальной отладки
(прямой `curl`/Postman в обход прокси) — см. известные ограничения.

## Мониторинг: Prometheus и Grafana

- **Метрики приложения** — `prom-client` (`src/middlewares/metrics.ts`): `http_requests_total`
  (счётчик, метки `method`/`route`/`status_code`) и `http_request_duration_seconds` (гистограмма
  с теми же метками) плюс стандартные метрики процесса Node (`collectDefaultMetrics`). Маршрут
  в метке — шаблон (`req.route.path`, например `/equipment/:id`), а не конкретный URL — иначе
  каждый UUID в пути породил бы собственную серию. Отдаются на `GET /metrics` (вне префикса
  `/api`, без rate limit и без аутентификации — так положено для Prometheus-эндпоинтов).
- **Prometheus** (`deploy/prometheus/prometheus.yml`) скрейпит `api:3000/metrics` каждые 15с и
  себя самого; правила алертинга — отдельным файлом `deploy/prometheus/alerts.yml`.
- **Grafana** поднимается в составе стека (`docker-compose.yaml`), источники данных и дашборд
  подключаются **автоматически** через provisioning
  (`deploy/grafana/provisioning/{datasources,dashboards}/`) — после `docker compose up` ничего
  донастраивать руками не нужно. Два источника:
  - `Prometheus` (`uid: prometheus`) — технические панели;
  - `PostgreSQL (read-only)` (`uid: postgres-readonly`) — прикладные панели прямыми SQL-запросами
    к той же базе, под read-only ролью `grafana_reader` (`db/init/20-create-grafana-reader-role.sh`,
    пароль — `GRAFANA_DB_PASSWORD`; роль имеет только `SELECT`, без `INSERT`/`UPDATE`/`DELETE` —
    проверено вживую, что запись от её имени падает с `permission denied`). Та же логика
    разделения прав, что и у `APP_PGUSER` для самого API.
- **Дашборд** `Equipment Maintenance — Overview`
  (`deploy/grafana/provisioning/dashboards/json/equipment-maintenance.json`) хранится в
  репозитории файлом и восстанавливается при развёртывании с нуля. Панели:
  - технические: интенсивность запросов (RPS по маршрутам), доля ответов 4xx/5xx, p50/p95
    времени ответа, `up{job="equipment-maintenance-api"}` (доступность сервиса);
  - прикладные: среднее время закрытия заявки (`avg(closed_at - created_at)`, те же часы, что
    и в `GET /api/sites/:id/summary` — см. [Модель данных](#модель-данных)), число просроченных
    плановых работ (`planned_at < now()` и статус ещё не терминальный), заявки по статусам и
    приоритетам, нагрузка на оборудование по площадкам, загрузка специалистов открытыми
    заявками, остатки запчастей ниже порога.
- **Алертинг** (`deploy/prometheus/alerts.yml`, через `alertmanager`):

  | Алерт            | Условие                                                       | Severity |
  | ---------------- | ------------------------------------------------------------- | -------- |
  | `ServiceDown`    | `up{job="equipment-maintenance-api"} == 0` 1 минуту           | critical |
  | `HighErrorRate`  | доля `5xx` среди всех ответов > 5% за 5 минут                 | warning  |
  | `HighLatencyP95` | p95 длительности запроса > 1с за 5 минут                      | warning  |
  | `NoTraffic`      | ноль запросов за 15 минут (подозрение на обрыв `nginx → api`) | info     |

  Порядок действий при срабатывании — см. [Эксплуатационная
  инструкция](#эксплуатационная-инструкция). `alertmanager.yml` сейчас маршрутизирует всё в
  один `receiver` без реального канала доставки (email/Slack/…) — подключение канала
  уведомлений вынесено в известные ограничения.

Проверено вживую: полный стек (`docker compose up --build`, включая снос тома `-v` для чистого
состояния) поднимается одной командой, `GET https://localhost/grafana/api/health` отвечает
`200 {"database":"ok"}` через `nginx`, оба датасорса проходят `health`-проверку Grafana
(`Database Connection OK`, `Successfully queried the Prometheus API`), запрос панели среднего
времени закрытия через API Grafana возвращает реальное число, посчитанное на сидовых данных.

## Эксплуатационная инструкция

- **Логи** — стандартный вывод контейнера (`docker compose logs -f api`), структурированные
  JSON-строки pino, уровень — `LOG_LEVEL`. У `nginx` — `access_log` в JSON (`json_combined`,
  `deploy/nginx/nginx.conf`) с `request_id`, что позволяет сопоставить запись nginx и запись
  приложения по одному и тому же `X-Request-Id`/`requestId` (см. [Логирование](#логирование)).
- **Метрики** — `GET /metrics` (внутри сети) и дашборд Grafana (`/grafana/` через `nginx`) —
  см. [Мониторинг](#мониторинг-prometheus-и-grafana).
- **БД недоступна** — `GET /api/health/ready` возвращает `503 SERVICE_UNAVAILABLE`, в логе —
  `error`-запись «база данных недоступна». Приложение не падает: `waitForDatabase()`
  переподключается при старте, а во время работы запросы к БД просто завершаются ошибкой,
  которую перехватывает `errorHandler`/`databaseErrorMapper`, а не роняет процесс. Проверить:
  `docker compose stop db`, затем `curl https://localhost/api/health/ready` — убедиться в
  `503`; поднять обратно `docker compose start db` — `/ready` должен вернуться к `200` без
  перезапуска `api`.
- **Рост доли 5xx** — сработает алерт `HighErrorRate` (см. выше). Дальше — панель «5xx error
  ratio» в Grafana, чтобы увидеть, растёт ли доля постоянно или это всплеск, и `docker compose
logs api | grep '"level":50'` (pino `error` = уровень 50) для стектрейсов за тот же период
  (по `requestId` из конкретных упавших запросов, если они уже известны).
- **Переполнение диска** — в первую очередь растут `pgdata` (WAL/таблицы) и `prometheus-data`
  (метрики хранятся `prometheus`'ом локально без retention-лимита в этом compose-файле).
  `docker system df -v` / `docker exec equipment-maintenance-db-1 df -h` — найти, какой volume
  растёт; для Prometheus — уменьшить `--storage.tsdb.retention.time` (не задан явно, значит
  действует дефолт самого образа) или поднять квоту диска; для Postgres — проверить, не
  скопились ли старые WAL-сегменты (`docker compose exec db psql -U app -c "SELECT
pg_size_pretty(pg_database_size(current_database()));"`).
- **Откат миграций** — `npm run db:migrate:undo` (последняя) или `npm run db:migrate:undo:all`
  (всё, включая ENUM-типы — см. [Миграции и сиды](#миграции-и-сиды)); `npm run
db:migrate:status` — что применено. Внутри контейнера: `docker compose run --rm migrate npx
sequelize-cli db:migrate:undo`.
- **Корректное завершение** — по `SIGINT`/`SIGTERM` (`src/index.ts`) сервер перестаёт принимать
  новые соединения (`httpServer.close()`), дообрабатывает уже начатые запросы и только потом
  закрывает пул соединений с БД (`sequelize.close()`) и завершает процесс; если штатное
  закрытие не уложилось в 10 секунд — принудительный `process.exit(1)`, чтобы контейнер не
  зависал при остановке/передеплое. `uncaughtException`/`unhandledRejection` логируются как
  `fatal` и тоже ведут к управляемому завершению, а не к падению в неопределённом состоянии.

Четыре файла (`unit/`, `databaseErrorMapper.test.ts`) — настоящие unit-тесты: чистые функции,

проверка прав по ролям, как того требует задание. Остальные — интеграционные: они реально ходят
в PostgreSQL («автотесты репозиториев и эндпоинтов на отдельной тестовой БД»), по определению не
могут быть unit-тестами.

Каждый тестовый файл поднимает `createApp()` заново (`tests/helpers/createTestApp.ts`) —
переменные окружения выставляются непосредственно перед динамическим `import('../../src/app.js')`,
поскольку конфигурация валидируется один раз при первом импорте `src/config`; так же, через
`NODE_ENV=test`, приложение подключается к `PGDATABASE_TEST`, а не к рабочей базе. БД
очищается (`tests/helpers/resetDb.ts`, `TRUNCATE ... CASCADE`) в `beforeEach`, а не в
`beforeAll` — то есть перед **каждым** тестом, а не один раз перед всем файлом: тест не может
случайно опереться на данные, оставленные соседним тестом того же файла. Каждый `it` либо
создаёт свои фикстуры заново в собственном `beforeEach`, либо явно заводит нужные ему сущности
внутри себя. Файл закрывает пул соединений в `afterAll` (`closeDatabase`) — Jest даёт каждому
тестовому файлу собственный модульный registry (свой инстанс `sequelize`), поэтому закрывать
пул нужно в каждом файле отдельно, иначе после прогона остаются висящие хендлы и Jest не
завершается сам. Проверено: каждый файл и даже каждый отдельный `it` (через `jest -t`) проходит
и в полном прогоне, и запущенным в одиночку — поведение не зависит от порядка выполнения.

Тестовые файлы гоняются **последовательно** (`maxWorkers: 1` в `jest.config.js`), а не
параллельно — они делят одну живую БД, и параллельная очистка таблиц одним файлом задела бы
данные другого. Обращение к внешнему погодному API в `tests/weather.test.ts` замокано
(`global.fetch`), поэтому тесты детерминированы и не зависят от сети.

Тесты выполняются в нативном ESM-режиме Jest (`node --experimental-vm-modules`) с транспиляцией
через `@swc/jest`; тайпчек тестов — отдельным конфигом `tsconfig.test.json` (основной
`tsconfig.json` собирает только `src/` в `dist/`).

## Postman

Коллекция и окружение лежат в [`docs/postman/`](docs/postman/):

- `equipment-maintenance-api.postman_collection.json`
- `equipment-maintenance-api.postman_environment.json`

Импортируйте оба файла в Postman, выберите окружение **Local**, при необходимости поправьте
`baseUrl`. Коллекция сгруппирована по ресурсам: `Auth`, `Health`, `Equipment`, `Requests`
(включая назначение/снятие бригады и историю статусов — они висят на пути `/api/requests/*`),
`Sites`, `Reports`, `Negative & security scenarios`.

Авторизация задана **на уровне коллекции** (`Bearer {{accessToken}}`) и наследуется всеми
запросами по умолчанию; публичные эндпоинты (health, `auth/register`, `auth/login`,
`auth/refresh`, `auth/logout`) явно переопределяют её на `No Auth`. Папку `Auth` нужно
прогнать первой — запрос «Login as admin» логинится под сидовым `admin@example.com`
(`db:seed`, пароль `ChangeMe123!`) и сохраняет access-токен в `{{accessToken}}`, на котором
держится весь остальной прогон; «Login as viewer» (последний запрос в папке — намеренно, чтобы
не перетереть cookie, на которой основан более ранний запрос «Refresh») сохраняет отдельный
`{{viewerAccessToken}}` для проверки `403` в `Negative & security scenarios`. Refresh-токен
Postman хранит сам, в cookie jar (`HttpOnly`-cookie с `path=/api/auth`) — «Refresh» и «Logout»
поэтому не требуют ручной передачи токена.

Использует `{{baseUrl}}` и переменные окружения для передачи идентификаторов между запросами
(`equipmentId`, `equipmentId2`, `requestId`, `serialNumber`). Для `Sites` и назначения бригады
в `Requests` дополнительно нужны `technicianId`, `technicianId2`, `siteId` — их не берёт ни
один эндпоинт, так как для специалистов и площадок задание не предусматривает своего CRUD,
поэтому значения в окружении захардкожены на конкретные id из демо-сида (`npm run db:seed`);
**без наполненной сидом БД запросы в `Sites` и назначение бригады в `Requests` вернут `404`.**

В каждом запросе есть `pm.test` минимум на код ответа и структуру тела. Папка `Auth` отдельно
проверяет, что пароль и хеш не попадают в ответы `register`/`login`/`me`. Папка
`Negative & security scenarios` проверяет: `400` (битый JSON), `401` (запрос без
`Authorization`), `403` (валидный токен viewer-роли на admin-only операции), `404`
(несуществующее оборудование/заявка/площадка, а также несуществующий специалист при назначении
бригады — с отдельной проверкой, что после отказа у заявки не осталось ни одного частично
применённого назначения), `409` (дубль серийного номера, недопустимый переход статуса,
повторное указание одного специалиста в списке бригады, перевод в `in_progress` без бригады —
каждый сценарий заводит собственную «подопытную» заявку через `prerequest`-скрипт под токеном
admin, не завязываясь на состояние других папок), `422` (тело не проходит схему валидации,
бригада без ровно одного `lead`) и `429` (rate limit — pre-request script отправляет пачку
запросов перед основным).

Все `prerequest`/`test`-скрипты, которые сами дёргают API (`pm.sendRequest`), написаны в
callback-стиле, а не через `await` — так коллекция одинаково проходит и в Postman Desktop, и
через `newman` (в части версий `newman` top-level `await` в скриптах даёт `SyntaxError`, из-за
которого guard-запрос тихо не создаётся, а связанная проверка молча получает не то состояние,
которое ожидает); эти же guard-запросы авторизуются `Authorization: Bearer {{accessToken}}` —
`pm.sendRequest` не наследует auth коллекции, это нужно делать явно. Коллекция целиком
прогнана через `npx newman run` на чистой, только что развёрнутой с нуля БД — **164 запроса,
100 проверок, 0 ошибок**.

Рекомендуемый порядок прогона — «Run collection» сверху вниз, либо папка за папкой
(`Auth → Health → Equipment → Requests → Sites → Reports → Negative & security scenarios`),
так как большинство запросов опираются на переменные (включая токен), сохранённые предыдущими.

## Индексы и производительность выборок

### Индекс под поиск (`ILIKE`) — `EXPLAIN ANALYZE` до и после

`?search=` в `GET /api/equipment` ищет подстроку в `name` **или** `serialNumber`
(`... ILIKE '%term%' OR ... ILIKE '%term%'`). У шаблона с ведущим `%` обычный B-tree индекс не
помогает — планировщик всё равно вынужден просматривать все строки. Добавлен GIN-индекс по
триграммам (`pg_trgm`, миграция `20260927100300-paranoid-unique-and-search-indexes`):

```sql
CREATE EXTENSION IF NOT EXISTS pg_trgm;
CREATE INDEX equipment_name_trgm_idx           ON equipment USING gin (name gin_trgm_ops);
CREATE INDEX equipment_serial_number_trgm_idx  ON equipment USING gin (serial_number gin_trgm_ops);
```

Замер сделан не на демо-данных (в них всего 8 строк — планировщик и так выберет `Seq Scan`,
эффекта не видно), а на 20 000 временно вставленных строк — честная демонстрация на объёме, где
разница вообще проявляется:

**До индекса** — `Seq Scan`, полный проход по таблице:

```
Seq Scan on equipment  (cost=0.00..645.12 rows=4 width=122) (actual time=4.331..17.822 rows=2 loops=1)
  Filter: ((name ~~* '%5000%') OR (serial_number ~~* '%5000%'))
  Rows Removed by Filter: 20006
Execution Time: 17.843 ms
```

**После индекса** — `Bitmap Heap Scan` с использованием обоих триграммных индексов:

```
Bitmap Heap Scan on equipment  (cost=43.00..57.77 rows=4 width=122) (actual time=0.261..0.264 rows=2 loops=1)
  ->  BitmapOr
        ->  Bitmap Index Scan on equipment_name_trgm_idx           (rows=2 loops=1)
        ->  Bitmap Index Scan on equipment_serial_number_trgm_idx  (rows=2 loops=1)
Execution Time: 0.318 ms
```

**17.8 мс → 0.32 мс** (~56×), план запроса сменился с полного просмотра на индексный доступ по
обоим полям. Временные строки после замера удалены, в демо-сиде их нет.

- `feat/docker` — multi-stage Dockerfile и `docker-compose.yaml`.

- `fix/models` — ограничения (`NOT NULL`, nullable `site_id`), расхождения между которыми
  вскрылись при явной сверке моделей с миграциями;
- `feat/seed` — сиды демо-данных;
- `feat/validation` — Zod-схемы под новые эндпоинты (`sites`, `reports`, `requestAssignee`,

Sequelize делались уже без строгого разделения на одну ветку под каждый файл — по объёму
работы это, по сути, один смысловой блок «перенос CRUD на PostgreSQL».

Кейс 4 (аутентификация, деплой, мониторинг) — тот же принцип, ветка на смысловой блок, слитая
в `main` через `git merge`:

- `fix/case-3` — донастройка окружения из замечаний по Кейсу 3 (роль `APP_PGUSER`, `dropEnum`
  в откате индексной миграции, `site_id` через API, поля `attributes` на выборках заявки и
  паспорта, вынос прямых обращений к моделям из `requestAssigneeService`/
  `requestStatusHistoryService` в репозитории);
- `feat/auth` — модель `User`/`RefreshToken`, RBAC (`requireRole`) и ABAC
  (`requestAuthorization`), JWT access/refresh, bcrypt, rate limit на вход;
- `feat/health` — `/api/health/live` и `/api/health/ready` вместо единого `/api/health`;
- `feat/openapi` — спецификация OpenAPI и Swagger UI (`/api/docs`);
- `chore/nginx` — обратный прокси, TLS, деплой-конфигурация (`deploy/nginx/`);
- `fix/style` — форматирование, `/api/health/*` на async-обработчиках, удаление
  отслужившей аутентификации по `X-API-Key`;
- `feat/monitoring` — метрики `prom-client`, стек Prometheus/Alertmanager/Grafana с
  provisioning, read-only роль `grafana_reader`.

Pull Request'ы с code review под каждую ветку — следующий шаг перед сдачей (см. [известные
ограничения](#архитектурные-решения-и-известные-ограничения)): сейчас ветки существуют и в
локальном репозитории, и в `origin`, слияние в `main` сделано напрямую через `git merge`.

## Архитектурные решения и известные ограничения

### Принятые решения

- **Слоистая архитектура** (роуты → контроллеры → сервисы → репозитории → модели) — сохранена
  без изменений от Кейса 2 до Кейса 4: аутентификация и мониторинг встроены в неё теми же
  приёмами (middleware, отдельные сервисы), а не добавлены поверх как сквозной хак.
- **RBAC на уровне роутера + ABAC на уровне сервиса** — ролевая проверка видна прямо в
  определении маршрута (`requireRole('admin')`), а привязка technician'а к конкретной заявке —
  дело предметной области, ей место в `requestService`, а не в middleware-слое, который о
  заявках ничего не знает.
- **Refresh-токен — отдельная таблица с хешем, а не "список строк" в cookie** — позволяет
  отозвать конкретную сессию, обнаружить повторное использование украденного токена и видеть
  историю входов (`userAgent`/`ip`), а не просто доверять подписи JWT до истечения срока.
- **Nginx как единая точка входа** — TLS, security-заголовки, таймауты и rate limiting первого
  уровня вынесены на границу стека; приложение остаётся простым HTTP-сервером и не дублирует
  логику, которая по-настоящему принадлежит прокси.
- **Grafana ходит в ту же БД под отдельной read-only ролью, а не через API** — прикладные
  панели (заявки по статусам, нагрузка на оборудование) быстрее и честнее строить прямым SQL
  по той же модели данных, что и у `reportRepository`/`siteRepository`, не изобретая
  отдельный «API для дашбордов»; `grafana_reader` физически не может ничего испортить.

### Известные ограничения

- **`/grafana/` за Nginx не ограничен дополнительно** (IP-allowlist/basic auth) — только
  собственным логином Grafana. Задание допускает любой из двух вариантов, но для
  производственного контура стоило бы добавить второй слой прямо в `nginx.conf`.
- **Порт `api` опубликован наружу напрямую** (`docker-compose.yaml`, для локальной отладки в
  обход прокси) — в чисто production-конфигурации его стоит убрать или ограничить
  `127.0.0.1`, как это уже сделано для `db`, чтобы единственным входом был `nginx`.
- **`Alertmanager` не подключён к реальному каналу уведомлений** (email/Slack/Telegram) —
  маршрутизация алертов настроена (`deploy/alertManager/alertmanager.yml`), но `receiver`
  пока один и без интеграции; это следующий шаг, не формальность «для галочки».
- **Pull Request'ы с ревью** по веткам Кейса 4 — ещё не оформлены на GitHub (см.
  [Git-флоу](#git-флоу)) — ветки есть, слияние выполнено напрямую.
- **HTTPS — самоподписанный сертификат**, генерируется локально (`tls-init`); для реального
  домена сюда нужен сертификат от внешнего CA (Let's Encrypt и т. п.), сама инфраструктура
  (редирект, заголовки, TLS-termination на Nginx) уже на месте и менять не придётся.
- **CRUD для площадок/специалистов отсутствует осознанно** — заданием не предусмотрен, они
  заводятся только сидом; `/api/users` — единственный «справочный» ресурс с полноценным CRUD,
  потому что роли и привязка к специалисту — часть требований Кейса 4.
- **Trade-off `paranoid` vs `onDelete`** — см. [Связи и целостность
  данных](#связи-и-целостность-данных): мягкое удаление оборудования выбрано вместо жёсткого
  каскада, чтобы не терять историю заявок; для специалистов и запчастей осталось простое
  `RESTRICT` без `paranoid` — удаления специалиста/запчасти через API всё равно нет.
